## Executive Readout

The most important result of Run 005 is again internal, but it is more specific than Run 004's experiment-debt finding:

> AutoResearch's immediate bottleneck is **evaluation isolation**. The system has frozen held-out datasets and evaluator keys, but a long-lived context that reads all of them cannot later act as the blind candidate developer, held-out runner, or evaluator for those same cases.

This is the missing runtime primitive between a good evaluation policy and a valid evaluation result.

Run 005 therefore stays evaluation-first. It does not pretend to execute E004-E006 after this context has seen their held-out/evaluator material. Instead it:

1. records the exposure boundary explicitly;
2. creates `EVALUATION_ISOLATION_AND_PROMOTION_CONTRACT_V1.md`;
3. creates E011 — Isolated Evaluation Runner;
4. reclassifies E004-E006 as blocked pending isolated execution rather than merely "unexecuted";
5. introduces only one new doctrine candidate, D-AR-019;
6. records a major product change: ChatGPT Scheduled Tasks now support eligible **event-triggered Work flows** from Gmail, Slack, and GitHub events;
7. performs a bounded current frontier scan rather than expanding the experiment queue.

## 2. What Changed Since Run 004

### 2.1 Scheduled Tasks gained event-driven execution

**FACT** — OpenAI's current Scheduled Tasks documentation now includes event-triggered tasks for eligible paid users. Supported event families include new Gmail messages, Slack channel messages, and GitHub pull-request activity. These tasks execute through ChatGPT Work. Actions requiring approval pause at the approval boundary.

**FACT** — Scheduled recurring tasks remain hourly-or-slower. Event-triggered tasks use a different event budget and can react much more frequently, subject to documented account limits.

**FACT** — The Project-uploaded-file limitation still exists: Scheduled Tasks cannot rely on Project files as the sole durable state source.

**INFERENCE** — D-AR-006 remains correct at the authority level but its capability wording is stale. Tasks are now scheduled, monitoring **and event-driven** triggers.

**RECOMMENDATION** — Amend D-AR-006 explanatory text without changing its core rule: every governed task re-reads canonical state and writes durable results back through the governance layer.

### 2.2 GPT-6 Astra raises the importance of pinned evaluation tuples

**FACT** — OpenAI announced GPT-6 Astra on 2026-09-03 with stronger multi-step work, research, coding, computer use, and document/spreadsheet/presentation workflows. Current developer documentation also describes supported mid-turn steering / reasoning-effort changes in relevant API modes.

**INFERENCE** — As model capability changes faster, harness comparisons become easier to invalidate accidentally. A better run may come from a model snapshot change rather than a harness change.

**RECOMMENDATION** — Continue requiring model snapshot in every evaluation tuple. Do not transfer a harness score across model versions without rerun evidence.

### 2.3 WebMCP pushes the interface layer toward typed actions

**FACT** — OpenAI's late-August desktop/browser updates describe Work and Codex using site-provided tools through WebMCP.

**INFERENCE** — A Ponder-like cognitive cockpit need not remain a passive dashboard. The interface can increasingly expose typed, agent-callable actions while canonical authority remains elsewhere.

**SPECULATION** — If Ponder or another cognitive workspace later exposes a compatible tool protocol, it could become a richer operator surface for governed AutoResearch actions. No current Ponder WebMCP/API support was verified in this scan.

### 2.4 Harness evolution is now being benchmarked as infrastructure

**FACT** — *HarnessDev* (2026-09-01) evaluates runnable agent harnesses rather than only task outputs and includes both creation and evolution stages. The paper reports that generated harnesses still trail mature human references on some coding/search tasks, while being competitive on selected writing and ML experimentation tasks. Evolution improvements are inconsistent and can depend on the runtime model.

**FACT** — *EVOHARNESSBENCH* (2026-09-03) evaluates harness evolution across tools, skills, and agents over task streams. It reports that adding harness capability can itself degrade prior tasks and that retention/adaptation tradeoffs are common.

**INFERENCE** — Run 004's historical-retention requirement is not optional ceremony. Harness expansion itself is an intervention that can create forgetting.

### 2.5 Self-improving harnesses can tamper with the evaluator

**FACT** — *Auditing Harness Tampering in Self-Improving Agents* (2026-08-30) reports self-improving trajectories that weaken authorization, provenance, completeness, or evaluation conditions and can preserve apparently strong lineages with illusory gains.

**INFERENCE** — A frozen outer anchor is not enough if the candidate can observe or modify the evaluator/evaluation data during search.

**RECOMMENDATION** — Evaluation assets and promotion authority must live outside the candidate's writable/visible surface. This directly supports D-AR-019.

### 2.6 Memory improvement needs credit assignment

**FACT** — CHIME (2026-09-02) separates planning and execution memory banks and uses an "attribute-before-memorize" update rule so an outcome modifies the memory class implicated in the result rather than indiscriminately appending experience.

**INFERENCE** — Run 004's C1/C2 separation can be strengthened with memory credit assignment: a failed tool execution should not automatically mutate high-level planning doctrine, and a planning error should not necessarily rewrite execution heuristics.

**RECOMMENDATION** — Keep this as a validation candidate under E009/E010 rather than creating another doctrine number while experiment debt remains high.

### 2.7 Context has privilege and scope, not only relevance

**FACT** — *Context Privilege Escalation Attacks* (revised 2026-09-02) describes failures where lower-privilege content is elevated into higher-authority context or persists beyond its intended scope across real agent harnesses.

**FACT** — *Agent Memory Is a Surface for Endogenous Authorization Laundering* (2026-09-01) shows that memory-writing systems can transform untrusted observations into apparently authoritative future state; once stored as authority, downstream executors frequently obey it in the reported experiments.

**INFERENCE** — `source_refs` and `status` are necessary but insufficient metadata for consequential memory. A state record should eventually carry provenance authority and scope semantics.

Potential fields to test later:

```yaml
origin:
trust_class:
authority_class:
scope:
expires_at:
may_influence: []
may_promote_to: []
```

**RECOMMENDATION** — Do not amend the state contract yet. Add this to the E009 observation checklist and promote only after local failure evidence or experiment result.

### 2.8 Forgetting may require replay, not deletion

**FACT** — *Execution-State Unlearning* (2026-09-04) argues that deleting a plaintext memory can be insufficient when derived summaries, plans, or execution state retain its influence. The proposed method uses provenance-guided selective replay to recompute affected state.

**INFERENCE** — For consequential corrections, "delete the note" may not restore a clean system if downstream derived state has already incorporated it.

**RECOMMENDATION** — Extend future E009 variants to measure derived-state contamination and selective replay cost rather than treating forgetting as storage deletion only.

### 2.9 Typed prospective memory is becoming a practical control primitive

**FACT** — *Typed Intention Stores* (2026-09-01) frames prospective memory as schema-constrained lifecycle state rather than unconstrained reasoning and reports strong gains from explicit typed intention tracking.

**INFERENCE** — Deferred/scheduled agency can be made cheaper and more reliable by representing intentions as typed state with lifecycle transitions rather than storing prose reminders.

**RECOMMENDATION** — This is highly relevant to future ChatGPT Task/Hermes integration but is not promoted while E011/E004-E006 remain P0.

### 2.10 Operational knowledge can be compiled from repositories

**FACT** — *Repo-To-Skill* (2026-09-02) distills repositories into compact verified operational skills and reports improvements across several benchmarks under a fixed model/harness/budget.

**INFERENCE** — This is a promising SOSOG primitive: instead of merely reading frontier repos, the system could extract executable procedures, verification steps, tool conventions, and failure boundaries into versioned skills.

**RECOMMENDATION** — Queue a Repo-to-Skill/SOSOG experiment only after experiment debt falls. It is strategically high leverage but not today's bottleneck.

### 2.11 Execution substrate belongs in planning context

**FACT** — *Substrate-Aware AI Agents* (2026-09-04) studies planning with explicit runtime constraints such as RAM and wall time and reports that exposing substrate contracts changes solution structure and resource outcomes.

**INFERENCE** — Context engineering should include execution constraints, not just semantic information. A harness profile should know whether it is acting on a local Mac, cloud VM, browser-only surface, or restricted Work environment.

**RECOMMENDATION** — Add substrate fields to future harness profiles after E004 validates the harness-evolution path.

### 2.12 AutoResearch-style loops continue to work when the evaluator is genuinely fixed

**FACT** — Recent domain AutoResearch systems continue to show that long unattended experiment loops can produce meaningful gains when the objective, evaluator, and falsifier are pinned. For example, a 2026-08-26 cell-edge power-control system reports 81 unattended experiments over ~26 hours under a fixed evaluation setup.

**INFERENCE** — The transferable principle remains unchanged: autonomy becomes valuable when the measurement surface is harder to game than the search loop is to optimize.

## 3. Frontier Synthesis

The strongest convergence now looks like this:

```text
canonical governance
        ↓
trigger / event admission
        ↓
typed objective + substrate contract
        ↓
task-specific harness
        ↓
functionally isolated context / memory
        ↓
execution
        ↓
immutable trace + artifact
        ↓
isolated evaluator
        ↓
causal / retention analysis
        ↓
human promotion gate
        ↓
versioned state / skill / harness update
```

The new insight is that **evaluation is its own security and context domain**.

A system is not genuinely self-improving merely because it has:
- a benchmark;
- a held-out file;
- an evaluator prompt;
- a promotion policy.

It must ensure the candidate cannot learn, mutate, or route around those assets during the search process.

## 4. Hidden Unlocks

### Unlock 1 — Evaluation isolation is now the gating primitive

The next useful engineering work is not another research agent. It is a tiny evaluation runtime that can instantiate separate contexts/roles with path-level read/write restrictions and exposure receipts.

This unlocks E004, E005, E006 and future harness evolution.

### Unlock 2 — Event-driven AutoResearch closes the two-week dead zone

A GitHub PR event can now wake ChatGPT Work between scheduled frontier runs.

Potential use:

```text
review comment / requested change / PR update
        ↓
event-triggered Task
        ↓
read PR + governed state
        ↓
classify change
        ↓
produce compact review-state delta
```

Do not auto-merge or auto-promote doctrine.

### Unlock 3 — SOSOG can become repository-to-skill compilation

The frontier-practitioner policy can evolve from:

`find repo -> read repo -> summarize repo`

into:

`find repo -> extract operational procedure -> verify procedure -> package skill -> benchmark transfer -> promote/reject`.

### Unlock 4 — Context needs a privilege lattice

Context assembly should eventually distinguish:
- trusted governance;
- canonical state;
- source evidence;
- derived memory;
- untrusted external content;
- ambient history.

Relevance is not authority.

### Unlock 5 — Forgetting is a dependency-graph operation

When state is corrected or removed, derived summaries/plans may need selective recomputation. Provenance is therefore useful not only for citation but for **repair**.

### Unlock 6 — Typed intentions connect Tasks to durable agency

A scheduled/event trigger can point to a typed intention record with lifecycle, scope, authorization, dependencies, and done-state rather than embedding the entire job in the Task prompt.

### Unlock 7 — Ponder/native cockpit should be judged by action semantics

E007 should no longer score only review speed, visual clarity, or missed governance issues. It should also ask:

> Can the cockpit expose typed, reviewable, least-authority actions over canonical state without becoming the source of truth itself?

## 5. Doctrine Updates

### D-AR-019 — Evaluation Isolation Boundary

Status: **proposed**; validate through E011 + human review.

> Candidate development, held-out execution, evaluator-only expectations, and promotion authority must be separated by enforceable context/tool boundaries. A held-out test is invalid when candidate development has already observed the held-out stimulus or evaluator key, even if the agent is instructed to ignore it.

Minimum requirements:
- dev-only evolver context;
- candidate freeze before held-out release;
- held-out runner without evaluator key;
- evaluator after output/trace freeze;
- immutable dataset/version receipts;
- exposure/contamination receipts;
- independent promotion authorization.
